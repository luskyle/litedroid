# 裁剪、部署与发布

## 每轮裁剪

1. 从未裁剪的 BSP 基线创建产品分支或独立工作区；记录厂商版本。
2. 盘点应用、常驻进程、外设、权限及服务依赖。
3. 在 `remove_packages` 中加入小批量已确认无用的 Make 产品包名。
4. 运行 `integrate`，人工将公共片段 include 放在板级产品所有继承之后。
5. 使用独立/干净输出构建 `product`，保留日志与 SHA-256。切换基线与产品时同样隔离输出，避免旧 APK 残留。
6. 检查实际镜像及刷机后的包/进程清单，验证业务和外设，记录相对基线的变化。
7. 不满足验收则在产品分支回退这一轮配置，重建并复测。

默认片段只做 `PRODUCT_PACKAGES` 过滤，不移除服务实现、驱动或权限 XML。电话/蜂窝、媒体、WebView、字体、语言、蓝牙和定位需要专项依赖审查，不能只删除 APK。不要删除 Settings、SystemUI、包管理、权限控制等组件作为首轮裁剪。

## 预装业务应用

拿到真实 APK/源码及包名后，按所选 BSP 的 Soong/Make 模式加入预装模块，并在公共产品配置中加入模块名。区分普通应用与确有必要的特权应用；特权权限需显式白名单并评审，不能简单使用平台签名获得全部权限。

优先通过 Launcher 或受支持的设备管理模式进入业务。限制用户入口时，同时设计维护授权、联网配置和故障恢复。正式版本不默认开放 root/ADB。

## 开发刷机

刷机前必须确认：

- 实物板卡/PCB 版本与 BSP 和镜像匹配。
- 厂商工具、分区格式及 bootloader 兼容。
- 目标设备身份明确，业务数据已备份；刷机可能清空数据。
- 已知恢复入口可用，串口/USB 接线和电源稳定。
- 镜像校验值匹配构建记录，不混刷不同版本的 boot/vendor/system。

使用厂商文档的准确刷机步骤。本仓库不提供猜测的 `fastboot flash` 或 Rockchip 分区写入命令。通用 `make` 产出的分区镜像不等于厂商可直接刷写的 `update.img`；如需打包，必须补上厂商指定的打包流程并记录校验值。

## 量产与 OTA 门禁

| 门禁 | 通过条件 |
|---|---|
| 版本可追溯 | BSP manifest/补丁、工程版本、应用版本、镜像哈希可追溯；发布工作区无未归档修改 |
| 构建可复现 | 环境与依赖版本已记录，独立环境可以重建；哈希记录本身不等于可复现 |
| 正式签名 | 使用受控的生产密钥，禁止使用公开 test keys；密钥不进入仓库 |
| 系统安全 | 生产构建类型合适，SELinux enforcing，AVB 按设备配置验证；关闭非必需调试口 |
| 恢复 | 实际执行升级失败、异常断电及故障恢复测试 |
| 升级 | 只启用 BSP 成熟支持的 A/B 或供应商升级方式，验证空间和回退能力 |
| 应用升级 | 校验签名、版本与系统兼容性，验证业务数据迁移和回退限制 |
| 外设与稳定性 | 全部必需外设、业务负载和长期运行测试通过 |

当前工程没有实现 OTA 服务、生产签名或量产自动刷机。不能凭 `build product` 成功就宣布量产就绪。A/B、动态分区、AVB 密钥轮换和防回滚机制必须按实际 BSP 设计，不能统一写死。
